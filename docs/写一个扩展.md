# 写一个扩展

> 这份是**动手教程**。要看字段全集、scope 表、错误码，去 `docs/API.md`（那边从源码生成，永远跟实现一致）。
> 面板里也能看：扩展 → 已安装 → 「想自己写？」那张卡，一键复制全文。

## 1. 扩展到底是什么

一个扩展 = **一个目录**，里面两份东西：

```
<数据目录>/extensions/weather/
├── plugin.json     ← 清单：告诉宿主「我叫什么、怎么启动我」
└── server.mjs      ← 一个 MCP server：告诉模型「我能做什么」
```

它**不是**框架插件（`plugins/` 里那种跑在 Roost 进程内的插件），而是一个独立进程，
和 DSH 之间走标准 MCP 协议。宿主不关心你用什么语言写 —— Node、Python、Go、编译好的 exe
都行，只要能说 MCP。

装好之后，你声明的每个工具会以 `mcp__<id>__<tool>` 的名字交给模型。
比如 id 是 `weather`、工具叫 `forecast`，模型看到的就是 `mcp__weather__forecast`。

## 2. 最快的一条路：先生成骨架

面板 → 扩展 → 已安装 → 「新建扩展」：

1. 填 **id**（小写英文，如 `weather-lite`）、**显示名**、**一句话说明**（这句给模型看，写清"什么时候该用我"）；
2. 选形态：`stdio`（宿主拉起你的进程）或 `streamable-http`（你自己起端口）；
3. 工具一行一个，写 `名字|说明`；
4. 点「生成骨架」。

生成的是**零依赖、能直接跑**的代码，两个文件，注释里标了「改这里」。
生成完面板会把一段「复制给 DSH 的话」放进剪贴板 —— 不会写代码的话，直接粘给 DSH，
把【】里那句换成你想要的，让它在这个骨架上改。

## 3. 手写：从零开始

### 3.1 放对位置

目录名必须**等于** `plugin.json` 里的 `id`，正则 `/^[a-z][a-z0-9-]{1,31}$/`
（小写字母开头，只含小写字母 / 数字 / 横线，2–32 位）。

放进 `<数据目录>/extensions/<id>/`。数据目录在哪：面板 → 扩展 → 已安装 → 「打开文件夹」。

### 3.2 最小清单

```json
{
  "kind": "dsh-extension",
  "id": "weather",
  "serverName": "weather",
  "name": "天气",
  "description": "查某个城市的天气",
  "transport": "stdio",
  "command": "node",
  "args": ["server.mjs"],
  "scopes": ["state:read"]
}
```

几条硬规矩：

- `kind` 必须是 `dsh-extension`（框架插件不带这个值）；
- `serverName` 必须等于 `id`；
- `stdio` 要 `command`（可执行文件名）和 `args`（参数数组）；`streamable-http` 要 `url`，**只认回环地址**；
- 清单里**不许写 `env`**：环境变量由宿主注入（`ROOST_API_URL` / `ROOST_EXT_ID` /
  `ROOST_LAUNCHER_DIR` / `ROOST_DEPS_DIR`），自己写会被忽略；
- `scopes` 不写 = 只有 `memory:write` + `state:read`。要发消息、要主动说话属于敏感项，
  安装时**主人得二次确认**，别指望静默拿到。**值必须逐字对上 `docs/API.md` §5 列出的项**
  （注意只有 `message:write`，没有 `message:read`）——写错一个字母，装的时候会被整份拒收。

### 3.3 一个能跑的最小 server（stdio）

```js
// server.mjs —— 零依赖：MCP 的 stdio 传输就是「一行一个 JSON」
import { createInterface } from 'node:readline'

const TOOLS = [{
  name: 'forecast',
  description: '查天气。参数 city 是城市名。',
  inputSchema: { type: 'object', properties: { city: { type: 'string' } }, required: ['city'] },
}]

const send = (msg) => process.stdout.write(JSON.stringify(msg) + '\n')
const rl = createInterface({ input: process.stdin })

rl.on('line', async (line) => {
  let req
  try { req = JSON.parse(line) } catch { return }
  if (req.method === 'initialize') {
    return send({ jsonrpc: '2.0', id: req.id, result: {
      protocolVersion: '2024-11-05',
      capabilities: { tools: {} },
      serverInfo: { name: 'weather', version: '0.1.0' },
    } })
  }
  if (req.method === 'tools/list') {
    return send({ jsonrpc: '2.0', id: req.id, result: { tools: TOOLS } })
  }
  if (req.method === 'tools/call') {
    if (req.params?.name !== 'forecast') {
      return send({ jsonrpc: '2.0', id: req.id, error: { code: -32602, message: `没有工具 ${req.params?.name}` } })
    }
    const city = String(req.params?.arguments?.city ?? '')
    // 这里换成你自己的逻辑
    return send({ jsonrpc: '2.0', id: req.id, result: {
      content: [{ type: 'text', text: `${city || '某个城市'}：晴，20℃` }],
    } })
  }
  // 通知（没有 id）不回复；未知请求给标准错误
  if (req.id !== undefined) {
    send({ jsonrpc: '2.0', id: req.id, error: { code: -32601, message: `没有方法 ${req.method}` } })
  }
})
```

Python 版同理：读 stdin 的每一行、解析 JSON、往 stdout 写一行 JSON。**不要往 stdout 打日志** ——
stdout 是协议通道，日志写 stderr，否则宿主会收到一行解析不了的垃圾。

### 3.4 想让扩展用 QQ 的能力

扩展不能直接连 QQ，要走宿主的 `/v1` 控制面：

- 地址在 `ROOST_API_URL`，令牌在 `ROOST_EXT_ID` 对应的 secrets 里（由宿主注入启动环境）；
- 能调什么由 `scopes` 决定，端点表见 `docs/API.md` §5–§6；
- 发消息、撤回、改群设置这类操作**会真发出去**，先在模拟器里试（面板 → 模拟）。

### 3.5 让扩展拥有聊天命令（框架 1.2.0 起）

扩展可以在清单的 `ui` 里声明几条聊天命令，群里直接发 `/命令名` 就能用。
框架在入站就拦下，转给宿主执行，宿主再转调扩展自己声明的动作：

```json
{
  "ui": {
    "runtime": "inprocess",
    "entry": "actions.mjs",
    "nav": { "label": "天气" },
    "view": { "kind": "log", "source": { "file": "data/log.json" } },
    "actions": [{ "id": "forecast", "label": "查天气" }],
    "commands": [
      {
        "name": "weather",
        "aliases": ["天气"],
        "desc": "查一个城市的天气",
        "action": "forecast",
        "admin": false,
        "ownerOnly": false
      }
    ]
  }
}
```

几条硬规矩：

- **只能转调已声明的动作**：`action` 必须在同一条 `ui.actions` 里出现过，
  否则整份清单判非法——命令不是「随便在宿主里挂一个入口」；
- 只有 `runtime: "inprocess"` 的扩展能挂命令：MCP 子进程拿不到同步回执，
  挂了也只会每次超时；
- `name` 小写字母开头、1–16 位；`aliases` 最多 3 个（中文可以）；
  `desc` 不超过 30 字；一个扩展最多 6 条；
- 权限 `admin` / `ownerOnly` 由**框架**按群里的角色判，扩展只声明；
- 动作收到的 `payload` 是 `{ command: { name, args, content }, msg }`，
  `msg` 与 `ext.call` 的载荷同形。返回 `{ reply: "..." }`（或直接返回字符串）
  就让框架替你发一条；不返回就认为你已经自己发过了。
- **与已有命令重名不会被丢掉**：框架把它改注册成 `<自报名>-<命令名>`
  （扩展是 `<扩展id>-<命令名>`，例如 `/bili-weather`），菜单里会写明
  「原名 /weather，与已有命令重名」。所以别假设自己声明的名字一定原样生效，
  用户看到的名字以 `/help 协议` 为准。

框架低于 1.2.0 时这些字段会被忽略——命令不生效，但扩展照常能用。

## 4. 改完怎么生效

扩展是 DSH 拉起的独立进程，**宿主不负责重连**（`docs/API.md` §1）。
所以改完代码要让它重新加载：

- 面板里改的**设置**（`config` 声明的那些）：保存后宿主会试着重连，不通会提示你重启 DSH；
- 改的是**代码或 plugin.json**：去 DSH 侧重连这个 MCP server，或者干脆重启 DSH。
  进程没重启的话，你改的代码不会生效 —— 这是本地开发最容易踩的坑。

## 5. 出错怎么排查

按这个顺序看，基本能定位：

1. **扩展压根没出现在列表里** → 看面板顶部「N 个扩展在目录里但清单不合格」那行，
   它会把 `plugin.json` 的具体错误列出来（字段缺失、id 和目录名不一致、transport 拼错）；
2. **装上了但模型看不到工具** → 工具名重复（宿主会静默丢掉后一个）、`inputSchema` 不是合法
   JSON Schema、或者扩展在启动时就崩了（stderr 里会有栈）；
3. **调工具报 401** → 令牌没注入（看你的启动环境有没有 `ROOST_EXT_ID`），
   或者面板里把它停用了；
4. **调工具报 403** → scope 不够。`docs/API.md` §5 有完整表，别靠猜。

## 6. 想发到市场

扩展市场和框架插件共用**同一份索引**（`qq-bot-roost-plugins` 仓的 `index.json`），
所以发布流程就是提一个 PR：

1. 把扩展目录放进仓库约定的扩展目录，附上 `README.md`（写清能力、scope、依赖）；
2. 跑仓库的索引生成脚本，把条目写进 `index.json`（别手改，脚本会算 sha256 和大小）；
3. 提 PR，说明它做什么、要哪些权限、怎么卸载干净。

进市场之后，别人在面板里点「安装」就能用；你后续更新版本时，
他们会看到「可更新」——但**用户本地改过的不会被覆盖**。

## 7. 让 AI 帮你写

不会写代码完全可以：面板 → 扩展 → 已安装 → 「复制给 DSH 的话」，
粘给 DSH（或任何编码 Agent），说清你想要什么。

那段话里已经写好了边界，照做就行：只改你那个扩展目录、先读同目录的 `API.md`、
改完告诉你重连/重启、别动宿主代码。
